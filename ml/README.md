# K-Runway ML + Monte Carlo (ต้นแบบด้วยข้อมูลจำลอง)

Pipeline **ข้อมูลธุรกรรม → ML → Monte Carlo → "วันนี้ใช้ได้เท่าไหร่" + โอกาสเงินพอ** ที่รันได้จริงตั้งแต่ต้นจนจบ ด้วย **ข้อมูลจำลองทั้งหมด** ไม่มีข้อมูลลูกค้าจริง

> ⚠️ ข้อมูลจำลองถูกสร้างโดยทีม รูปแบบที่ ML จับได้ (วันในสัปดาห์ ช่วงหลังเงินเข้า ลูกค้าที่จ่ายช้า) เป็นสิ่งที่เราใส่เข้าไปเอง ผลจึง **พิสูจน์ว่าระบบทำงานถูกตามตรรกะและวัดผลได้** แต่ **ไม่ได้พิสูจน์ว่าแม่นกับข้อมูลจริง** ห้ามอ้างตัวเลขเหล่านี้เป็นความแม่นยำของ K-Runway

## วิธีรัน

```bash
cd ml
uv venv .venv && uv pip install -p .venv/bin/python -r requirements.txt   # ครั้งแรกครั้งเดียว
.venv/bin/python run.py                          # 300 คน ~1 นาที → output/
.venv/bin/python run.py --quick                  # 60 คน เช็กเร็ว ๆ → output/quick/
.venv/bin/python -m unittest discover -s tests   # เทสต์ 10 ข้อ
```

```
│   ├── data.py         สร้างข้อมูลจำลอง 3 กลุ่ม (เงินเดือนประจำ / ฟรีแลนซ์ / มีงานเสริม) 270 วัน
│   ├── model.py        หาบิลประจำ, ML พยากรณ์รายจ่าย, โมเดลวันเงินเข้า

```

## หลักการทำงาน

1. **หาบิลประจำ:** จ่ายผู้รับเดิม ≥ 3 ครั้ง ยอดใกล้กัน ห่างกันราว 1 เดือน
2. **ML พยากรณ์รายจ่าย:** `HistGradientBoostingRegressor` ทำนายรายจ่ายแต่ละวันเทียบกับระดับปกติของผู้ใช้ จากวันในสัปดาห์ วันในเดือน วันนับจากเงินเข้า ระดับรายจ่าย และยอดเงินเทียบรายจ่าย ใช้ residual เป็นความไม่แน่นอนรายวัน และเพิ่มความผันผวนรายเดือน
3. **วันเงินเข้า:** เรียนรู้จากประวัติว่าผู้จ่ายแต่ละรายมักจ่ายช้าแค่ไหน ผสมกับค่ากลางของธนาคาร (ผู้จ่ายใหม่ใช้ค่ากลางไปก่อน)
4. **Monte Carlo:** จำลอง 4,000 เส้นทาง × 30 วัน ในแต่ละเส้นทาง รายจ่าย = งบ × รูปแบบการใช้ จึงหางบสูงสุดที่ไม่ติดลบได้ตรง ๆ
   `งบสูงสุด[เส้นทาง] = min ทุกวัน ( เงินที่มีถึงวันนั้น ÷ รูปแบบการใช้สะสม )`
   งบที่ได้โอกาสพอ 85% = quantile ที่ 15% ของงบสูงสุด

## ผลลัพธ์

### 1) ตัวอย่างในสไลด์

เงิน ฿9,000 / ค่าห้อง ฿3,500 วันที่ 5 / ค่าจ้าง ฿8,000 คาดเข้าวันที่ 12 (ตรงเวลา 60%, ช้า 6 วัน 30%, ช้า 13 วัน 10%) / ใช้ปกติวันละ ฿395

| สถานการณ์ | งบต่อวัน | โอกาสเงินพอ 30 วัน |
|---|---|---|
| หารเท่า ๆ กัน | ฿450 | – |
| ใช้ปกติ และค่าจ้างเข้าตรงเวลาเสมอ | ฿395 | 81% |
| ใช้ปกติ แต่ค่าจ้างอาจเข้าช้า | ฿395 | **52%** |
| ลดเหลือ ฿280 | ฿280 | 86% |
| **ยอดที่ระบบแนะนำ (เป้า 85%)** | **฿284** | 85% |

### 2) Backtest (300 คน × 9 จุดเริ่ม × 30 วัน = 2,700 กรณีต่อวิธี)

เทรนด้วย 180 วันแรก ทดสอบกับช่วงหลังที่โมเดลไม่เคยเห็น แต่ละวิธีแนะนำงบต่อวัน แล้วเล่นซ้ำสิ่งที่เกิดจริง (วันเงินเข้าจริง บิลจริง และจังหวะการใช้เงินจริงของผู้ใช้)

| วิธี | เงินหมดเมื่อทำตามคำแนะนำ |
|---|---|
| (ก) หารเท่า ๆ กัน | **73%** |
| (ข) คำนวณตรงตามวัน (คิดจังหวะ แต่ไม่คิดความไม่แน่นอน) | 60% |
| **(ค) K-Runway: ML + Monte Carlo (เป้าโอกาสพอ 85%)** | **23%** |

| เงินหมด (%) | หารเท่า ๆ กัน | คำนวณตรง | K-Runway |
|---|---|---|---|
| ฟรีแลนซ์ | 74 | 69 | **26** |
| เงินเดือนประจำ | 68 | 53 | **20** |
| มีงานเสริม | 77 | 58 | **22** |

Calibration: ตั้งเป้า 85% → พอจริง 82% อีกราว 7% ของกรณี แม้ไม่ใช้เงินเลยก็ไม่ถึงเป้า ระบบควร **เตือน** แทนการให้งบ (ตัวเลข 23% ข้างบนนับกรณีเหล่านี้เป็น "เงินหมด" ด้วย)

### 3) ทดสอบรายส่วน (`model_checks.csv`)

| เรื่อง | ML | วิธีเปรียบเทียบ |
|---|---|---|
| พยากรณ์รายจ่าย 30 วัน คลาดเคลื่อน (median) | **17.4%** | 25.6% (ค่าเฉลี่ย 7 วันล่าสุด) |
| ทำนายว่าเงินก้อนไหนจะเข้าช้า (AUC) ทุกรายได้ | **0.82** | 0.72 (ดูแค่ประเภทผู้จ่าย) |
| ทำนายว่าเงินก้อนไหนจะเข้าช้า (AUC) เฉพาะลูกค้าฟรีแลนซ์ | **0.70** | 0.50 (เท่ากับเดาสุ่ม) |
| เตือนเมื่อโอกาสพอ < 70%: จับคนที่เงินหมดจริงได้ | **93%** | – |
| เตือนเมื่อโอกาสพอ < 70%: เตือนแล้วถูก | **78%** | – |

### อ่านผลอย่างตรงไปตรงมา

- **ตัวที่ลดการเงินหมดมากที่สุดคือการคิดเผื่อความไม่แน่นอน (Monte Carlo):** แค่คิดจังหวะเงินเข้า–ออก (ข) ยังเงินหมด 60%
- **จุดที่การเรียนรู้จากประวัติรายบุคคลช่วยชัดที่สุด คือรู้ว่าลูกค้ารายไหนมักจ่ายช้า** (AUC 0.70 เทียบกับเดาสุ่ม 0.50) จึงช่วยกลุ่มฟรีแลนซ์
- **ML มั่นใจเกินจริงเล็กน้อย** (บอก 85% พอจริง 82%) ระบบจริงต้องปรับเทียบ (recalibrate) ด้วยข้อมูลย้อนหลังของธนาคาร
- **ห้ามอ้างว่า ML แม่นกว่า X%** บนข้อมูลจริง เพราะผลนี้มาจากข้อมูลที่เราสร้างเอง

## ข้อจำกัด

1. **ขอบเขต 30 วัน:** ถ้ามีเงินก้อนใหญ่เข้าในช่วงนั้น ระบบอาจแนะนำงบสูงกว่าที่ใช้ปกติมาก ระบบจริงควรจบช่วงที่ "เงินก้อนถัดไป" และกันบิลของรอบหน้า
2. **เงินที่รอเข้า:** สมมติว่าผู้ใช้กรอกไว้ครบ และได้เงินครบตามยอด
3. **ข้อมูลที่มองไม่เห็น:** เงินจากธนาคารอื่น BNPL นอกแอป และเงินสด
4. **บิลในข้อมูลจำลองยอดเท่ากันทุกเดือน:** ของจริง (เช่น ค่าไฟ) ยากกว่า

## แผนพิสูจน์ผลกับข้อมูลจริง

1. **Backtest ภายในธนาคาร** ด้วยข้อมูลย้อนหลังแบบไม่ระบุตัวตน `krunway/backtest.py` ใช้ได้ทันที เพราะรับข้อมูลรูปแบบเดียวกับ `output/data/` (ผู้ใช้, วัน, เข้า/ออก, ผู้รับ/ผู้จ่าย, ยอด)
2. **ตรวจ calibration** ด้วยกราฟเดียวกับ `calibration.png`
3. **Pilot แบบ A/B 3 เดือน** วัดจำนวนครั้งที่เงินหมดหรือต้องกู้ประคอง ยอดออมใน Pocket และอัตราปิดการแจ้งเตือน
